# AgroBridge engine  (install44)

Pure decision logic. **No Firebase, no React, no `Date.now()`, no imports from `../services`.**
Every function: plain inputs → plain outputs. That is what lets the *same files* run

* today — in the browser (`services/bookings.js` is the "local adapter": it reads Firestore, calls the engine, writes the result), and
* tomorrow — in Node.js on the AgroBridge server, behind an HTTP API, unchanged.

```
screens/            shows things; calls services/*
services/bookings   LOCAL ADAPTER  (Firestore in/out)  ── later: serverAdapter (fetch)
engine/capacity     planner: quintals/hour windows, buffer, 1+3 runs, close-hour
engine/models/      A correction.js  (Bayesian shrinkage)   declared → expected q
                    B throughput.js  (EWMA per hour)        real q/h from weighings
                    C noshow.js      (logistic regression)  P(farmer shows)
                    params.js        learned weights  ← generated by ml/train_noshow.py
ml/                 make_dataset.py (synthetic season), train_noshow.py (scikit-learn)
```

Prove it works outside the app:  `node engine/selftest.mjs`
Play a whole season and watch it learn:  `node simulate.js --reset --days 10`  (see ML-SIMULATION-GUIDE.md)

Retrain:  `python ml/make_dataset.py && python ml/train_noshow.py`
(replace `ml/data/bookings.csv` with a real export when you have one, then
`AGB_DATA_SOURCE=real-export python ml/train_noshow.py`).

Rules for anyone editing this folder
1. Never import anything from `services/` or `firebase`.
2. Time comes in as a parameter (`nowMs`), never from the clock.
3. Learned numbers live in `models/params.js` or `centre.engine.localParams`, never in screens.
4. The planner must be **deterministic**: same inputs → same answer (the booking
   transaction re-runs it and relies on that).
